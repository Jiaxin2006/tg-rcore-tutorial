## 一、与AI合作的实现过程

1. 如何与AI交互

我写代码的时候大部分时间使用 cursor 的 auto 模型，pormpt 中我倾向于按条列出我希望它做的事情，这样它会给自己列一个 todo list 并完成，比纯粹的 chat 更不容易漏点。同时，虽然 context length 没有超，但是模型也会遗忘，需要自己把需要模型注意的点强调出来。ch5 之后我发现 auto 比较笨，于是换成了 GPT-5.3 Codex。不过模型太聪明了也有缺点 —— 会丧失一些从它的错误中学习的机会。

cursor 相比部分 coding 工具的一个好处是它会展示出修改了哪些部分并可以回退。因此在赶时间的时候能够清晰地看出任务的主干代码是什么；有时间的时候也可以把修改部分删掉，重写一遍函数功能，并和 ai 的实现做对应，以此练习自己对操作系统架构和rust语法的掌握。在完成之后，我还会请 ai 给我针对这次实验提几个问题，以检查自己知识层面的理解。

在做 T2 时，我会先把飞书上的题目 + 我自己对实现的理解（功能的具体定义等）输入给AI，请它帮我添加一个定义和函数框架；随后，我再手动检查框架的定义是否合理，并逐个与 AI 协同实现函数。常常，我发现 AI 会偷懒，比如现有接口能够得到一个可能说通但其实并不正确的功能调用，它就不会实现新的接口，于是需要人工审核 + 调整。

T2L4 要嵌入内核需要实现的内容太多了，考虑到同学的实现难度需要与其他实验平齐并能够实现、比较更多算法，我要求AI实现了一个模拟器，测试的时候用真实情境的代表任务。

2. 碰到的问题/bug

ch3: 出现了两处语法 bug：一个是带 unsafe 的类型转换没有加括号，一个是函数中没有直接把id 声明成 SyscallId 导致编译器推断的时候目标类型不明确。以及我发现syscall 使用静态表存储会超出内核栈。
打包的时候发现因为编译环境不一样导致出现了 未使用变量 的错误。

ch4: 再次出现了 unsafe 类型转换没加括号的问题（我并没有开新的对话，说明大模型的长上下文信息追溯能力还是有问题）；而且大模型自动了理解为syscall 调用次数的统计不再需要因此没有实现，且在我让他实现的时候实现的还是 内核cache 会爆炸的版本。打包的时候又出现了变量未使用错误，发现只要有只在 exercise 下用到的代码就会报类似错误，每次都改比较麻烦。

ch5-6: 这两次我给 ai 的 prompt 中加上了过去已经出现过的 bug 提示，以避免它无法 retrieve 过去的聊天记录并吸取教训。整体没碰到什么 bug。

ch6 和 ch8: 打包的时候遇到了 Cargo.toml 文件中依赖的仍是过去版本的 efs/sync，导致crates 上传的时候编译报 method not found.

T2L4: starvation 的统计，由于 stats 里面实现了总 waiting 时间，模型自动生成的代码就直接调用了这个数据，而不是比较当次 waiting 时间和 threshold。

T2L5: 我发现 mutex release 的时候没有先把 locked 参数释放掉，被唤醒的线程又重新入队等待，导致陷入死锁。而且，尽管我给了 prompt，AI 自动实现的测试任务无法满足失败情况的监测。

在做 T3 的时候，我发现直接把所有信息都提供给 AI 并期待它直接进行实现，由于 demo 的复杂性和 coding 模型在多模态能力（处理图像信息）的局限性，会导致极长的思考过程，以至于无论从模型生成结果的可靠性还是从我自己的 token 余量来说都不可行。

T3L1: 一开始我尝试先把 VirtIO-GPU 和 framebuffer 接口搭好，再让模型根据参考图自动推断七巧板的摆放方式。但由于当前 coding 模型对图像的几何关系理解并不稳定，它更容易给出“颜色大致对、比例和位置不对”的结果；如果继续让它黑箱式自动调整，不但 token 消耗很大，而且很难判断每次修改到底是否更接近目标。

3. 解决过程

ch3: 语法错误直接把 bug 描述喂给 ai 就能解决（不过错的比较低级，手动修或许更快）。ai 写代码的时候不会考虑太多复杂情况和边界条件，导致栈溢出这类错误还是要靠人来发现。

ch4: 手动修改括号，并从 ch3 的代码 merge。发布到 crates 时添加 `--features exercise`.

ch6/8: 打包对应的依赖组件，也上传到 crates 上。

T2L4: 增加保存上次状态改变时间，以便统计。

T2L5: 手动推演了一遍锁逻辑并要求 AI 修改。把想要设计的实验逻辑也告诉 AI，使它可以帮我写出检测出错的test。

T3: 请它先帮我规划需要怎么实现，我审核后请它一个一个实现对应的函数代码，这样既有利于 code review，也使得有些部分（比如七巧板的摆放）能够由我来更方便地调整，而不是由它直接实现出来。

T3L1: 后来我先让 AI 规划并逐步实现底层部分：QEMU 图形 runner、VirtIO-GPU 初始化、framebuffer 写入与 flush、最小栅格化函数。七巧板摆放本身则改成“人审阅 + AI 协助改坐标”的方式：一度尝试过“标准七巧板积木 + 定点坐标旋转”的参数化模型，但它对这道题反而过于复杂，相当于把“摆图”问题套成了两层变换。最后回到更直接的方案：在 `tangram.rs` 中用 `Piece::Tri` / `Piece::Quad` 和顶点数组直接描述参考图中的每一块，并额外保留 `render_piece` / `render_progressive` 等接口，方便后续 ch2 做逐块显示。

## 二、T1 学习效果评估

1. 自己在这个学习过程中知识和能力的提升/下降评价

- 和 ai 合作的时候能从它的思考过程中学到很多 检查代码结构、debug 的方法。
- 整体实验内容和校内小实验差别不大，思想都很一致，所以更像是一遍复习。

1. 与本校现有教学实验教程的定量/定性的对比分析

- 完成时间：现有教学实验我的完成节奏大约是3天一个 Chapter；而这次的实验我大概三天就全部完成了。
- 难度体会：不知道是不是和做过了本校小实验有关，感觉这一版实现起来好像容易一些。从修改行数来看，代码量基本差不多。对大部分同学的水平而言，我猜想框架的差别对难度的影响远不如学 Rust 语言带来的难度。

## 三、T2L4 学习效果评估

### 1. 定量指标

**覆盖度对比**


| 维度   | 原实验（ch3-ch8）                     | 我的扩展实验（exp4）                                                                              |
| ---- | -------------------------------- | ----------------------------------------------------------------------------------------- |
| 调度算法 | FIFO/RR + stride（ch5 练习）         | FCFS / SJF / RR / MLFQ / CFS-like（5 种）                                                    |
| 调度接口 | `Schedule { add, fetch }`（2 个方法） | `PluggableScheduler { enqueue, pick_next, on_tick, on_block, on_wakeup, on_exit }`（6 个方法） |
| 可观测性 | 无统一指标，只看"用户程序能否跑通"               | 统一 `MetricsCollector` 采集 7 种事件，输出 6 项指标                                                   |
| 测试体系 | 功能验收（`test.sh`，检查输出字符串）          | 脚本化 workload × 3 组 + 自动对比表 + 可重复运行                                                        |


**性能/行为对比（exp4 Mixed workload 实测数据）**


| 指标       | FCFS   | SJF    | RR-10  | MLFQ-3     | CFS    |
| -------- | ------ | ------ | ------ | ---------- | ------ |
| 平均等待时间   | 72.60  | 69.80  | 61.80  | **36.20**  | 38.40  |
| 平均周转时间   | 110.80 | 108.00 | 98.20  | **72.80**  | 72.40  |
| 吞吐量      | 0.0329 | 0.0360 | 0.0407 | **0.0407** | 0.0407 |
| 交互延迟 P95 | 43     | 56     | 23     | **7**      | 9      |
| 饥饿次数     | 4      | 4      | 0      | **0**      | 0      |


关键结论：

- MLFQ 和 CFS 在混合负载下表现最优，交互延迟 P95 从 FCFS 的 43 降至 7（降幅 84%），饥饿完全消除
- SJF 的 P95 反而比 FCFS 更差（56 vs 43），因为它按总 burst 排序，交互型短任务被长任务的"短估计"挤占
- 原实验的 stride 调度无法直接比较（它解决的是"按优先级比例分配 CPU"，而非"减少交互延迟"）

**原实验 vs 新实验的接口对比**


|         | 原 `Schedule`       | 新 `PluggableScheduler`                   |
| ------- | ------------------ | ---------------------------------------- |
| 时钟中断感知  | 无（外部硬编码抢占）         | `on_tick` 回调，策略自主决定是否抢占                  |
| 阻塞/唤醒感知 | 无（外部直接 add/remove） | `on_block/on_wakeup`，策略可调整优先级            |
| 退出清理    | 无                  | `on_exit`，CFS 可清理 vruntime               |
| 时间戳     | 无                  | 所有方法接收 `now: Tick`                       |
| 数据采集    | 无                  | 统一 `SchedEvent` 事件流 + `MetricsCollector` |


### 2. 定性指标

- **系统理解提升**：从"知道 MLFQ 是多级队列"到"知道时间片到期时降级、on_block 时不降级、boost_all 防饥饿"这些具体实现细节。尤其是在实现 `record` 函数时，搞清楚了 Preempt（回就绪队列，累计 wait_ticks）和 Block（进阻塞态，不算等待 CPU）的本质区别。
- **工程能力提升**：学会了"策略与机制分离"的设计模式——同一套 `PluggableScheduler` trait 可以插入任意调度算法，不需要改内核其他代码。理解了"两阶段记账"（连续时间结算 + 离散事件处理）的统计方法。
- **抽象能力提升**：把 5 种调度算法统一到一个 trait 下，发现它们的本质差异只在 `pick_next` 的选择策略和 `on_tick` 的抢占判断上。
- **代价**：模拟方式虽然更容易做定量对比，但缺少真实内核中的中断/并发问题（如调度队列需要关中断保护），这部分体验不如原实验。

### 3. 与本校现有实验教程的对比分析


| 对比维度     | 原教程（ch5 stride）                  | 我的实验（exp4 调度套件）                      |
| -------- | -------------------------------- | ------------------------------------ |
| **覆盖范围** | 1 种算法（stride）                    | 5 种算法 + 可扩展                          |
| **教学结构** | 读代码 → 填实现 → 跑测试通过                | 读概念 → 统一接口 → 实现 → 定量对比 → 分析          |
| **测试体系** | 功能验收（字符串匹配）                      | 脚本化 workload + 自动输出 6 项指标            |
| **可扩展性** | 改 `fetch` 函数，耦合在 `ProcManager` 里 | 实现 `PluggableScheduler` trait 即可，零耦合 |
| **可复现性** | 依赖 QEMU + 内核编译环境                 | `cargo test` 直接跑，无环境依赖               |
| **反馈速度** | 编译内核 + 启动 QEMU + 运行用户程序（~30s）    | `cargo test`（< 1s）                   |


## 四、T2L5 学习效果评估

### 1. 定量指标

**覆盖度对比**


| 维度 | 原实验（ch8） | 我的扩展实验（exp5） |
| ---- | ---- | ---- |
| 同步原语 | MutexBlocking / Semaphore / Condvar（3 种） | SpinLock / MutexBlocking / Semaphore / Condvar / RwLock（5 种） |
| 同步接口 | `Mutex { lock, unlock }`（2 个方法） | 统一 `Mutex` trait + 各原语阻塞式 API（`acquire/release`、`read_lock/write_lock`） |
| 可观测性 | 无量化指标，只看"死锁检测能否触发" | 统一 `SyncMetrics` 采集 7 项指标 + `InstrumentedMutex` 装饰器自动记录 |
| 测试体系 | 功能验收（用户程序能否跑通） | 正向 + 反向 + 压力 + 对比共 22 个测试，脚本化可重复 |
| 经典场景 | 无 | 生产者-消费者、读者-写者、哲学家就餐 |


**性能/行为对比（exp5 实测数据）**


| 指标 | Mutex+Sem (ProdCons) | RwLock (RW) | MutexBlocking (RW) | Ordered (DinPhil) | Unordered (DinPhil) |
| ---- | ---- | ---- | ---- | ---- | ---- |
| 竞争次数 | 1359 | 374 | 759 | 4 | 75 |
| 获取次数 | 1600 | 1600 | 1600 | 500 | 12 |
| 平均等待(us) | 22.3 | 102.7 | 122.9 | 2038.0 | 13447.9 |
| 最大等待(us) | 161 | 1593 | 871 | 3410 | 202104 |
| 上下文切换 | 768 | 111 | 759 | 4 | 6 |
| 饥饿次数 | 0 | 0 | 0 | 0 | 0 |


关键结论：

- **RwLock vs MutexBlocking（读者-写者场景）**：RwLock 的竞争次数降低 51%（374 vs 759），上下文切换降低 85%（111 vs 759），因为多读者可并发进入临界区而无需排队
- **有序 vs 无序哲学家就餐**：无序模式触发死锁，仅完成 12/500 餐（2.4%）；有序模式 500 餐全部完成，平均等待时间降低 85%
- **Spin vs Sleep 对比**：轻负载（800 ops）下 SpinLock 177μs vs MutexBlocking 179μs，差异很小；但自旋锁在高竞争 + debug 模式下需要 TTAS + 退避策略才能正常工作

**反向测试覆盖（每个原语一个"故意出错→检测超时"的对照）**


| 原语 | 故意的错误 | 检测方式 | 预期 |
| ---- | ---- | ---- | ---- |
| SpinLock | acquire 后不 release | 500ms 超时检测 | 第二个 acquire 永远卡住 |
| MutexBlocking | acquire 后不 release | 500ms 超时 + try_acquire_timeout | acquire 卡死，try 返回 false |
| Semaphore | acquire 后不 release/up | 500ms 超时 + down() 返回值 | 第二个 acquire 永远阻塞 |
| Condvar | 注册等待者后不 signal | waiting_count 检查 | 队列保持非零 |
| RwLock | write_lock 后不 unlock | 500ms 超时（分别测读者和写者） | read_lock 和 write_lock 全部卡死 |

**原实验 vs 新实验的接口对比**


| | 原 ch8 `Mutex` | 新 exp5 扩展 |
| --- | --- | --- |
| 自旋锁 | 无（仅内核 `UPIntrFreeCell`） | `SpinLock`：TTAS + 指数退避 |
| 读写锁 | 无 | `RwLock`：读者并发 / 写者独占 |
| 指标采集 | 无 | `InstrumentedMutex` 装饰器，7 项指标 |
| 阻塞式 API | 无（由内核调度器处理） | `acquire/release`：用户态直接阻塞 |
| 超时获取 | 无 | `try_acquire_timeout`：可检测死锁 |
| 公平性分析 | 无 | 变异系数（CV）+ 每线程等待时间分布 |


### 2. 定性指标

- **同步语义理解提升**：从"知道信号量就是 P/V"到理解 `release()` 中 `locked` 标志必须先释放再唤醒等待者，否则被唤醒线程看到 `locked=true` 又会重新入队形成死锁。这种在实际多线程环境下的 bug 排查经历比看教科书深刻得多。
- **硬件架构感知**：在 ARM64 (Apple Silicon) debug 模式下发现纯 CAS 自旋锁会活锁，理解了 LDXR/STXR 指令在多核缓存争抢下的特性，以及 TTAS（Test-and-Test-And-Set）+ 指数退避的必要性。
- **并发 bug 调试能力**：学会了通过"手动推演多线程时序"定位 release 的死锁 bug 和 producer-consumer 消费者终止竞态条件，以及用超时机制将"挂起"转化为可检测的测试断言。
- **设计模式**：`InstrumentedMutex<M: Mutex>` 用装饰器模式把指标采集与同步原语解耦——任何实现了 `Mutex` trait 的类型都可以被包装，不修改原始代码就能观测行为。
- **代价**：用户态模拟无法体验内核中的关中断保护和真实调度器交互（如 `make_current_blocked` / `re_enque`），对中断上下文下的同步问题（如中断处理程序中不能用睡眠锁）缺乏直接体验。

### 3. 与本校现有实验教程的对比分析


| 对比维度 | 原教程（ch8 死锁检测） | 我的实验（exp5 同步套件） |
| ---- | ---- | ---- |
| **覆盖范围** | 3 种原语（Mutex/Sem/Condvar） | 5 种原语 + InstrumentedMutex 装饰器 |
| **教学结构** | 读代码 → 实现银行家算法 → 跑通测试 | 实现原语 → 正向/反向测试 → 经典场景 → 定量对比 |
| **测试体系** | 功能验收（检测到死锁即通过） | 22 个测试：正向 5 + 并发 4 + 反向 7 + 对比 6 |
| **反向验证** | 无（只有正向"能跑通"） | 每个原语故意出错 → 超时检测 → 断言失败 |
| **可观测性** | 无量化指标 | 7 项指标 + 对比表 + 公平性 CV |
| **可复现性** | 依赖 QEMU + 内核编译环境 | `cargo test`（< 10s） |

### 2. 定性指标

- **系统理解提升**：相比单纯打印 `Hello, world!`，这次真正把“操作系统如何驱动显示硬件”走通了一遍。虽然使用的是 QEMU 提供的 VirtIO-GPU，而不是实体显卡，但我已经能把“设备发现 -> 初始化 -> 申请 framebuffer -> 写像素 -> flush 到窗口”的路径串起来理解。
- **抽象设计体会**：一开始我倾向于把七巧板做成“标准积木 + 旋转/缩放”的参数化系统，后来发现这会让题目本身被抽象过度。最后改成直接维护顶点数组之后，代码更短、更容易核对参考图，也更适合做人工微调。这让我更清楚地认识到：抽象并不是越多越好，应该为当前任务服务。
- **与 AI 协作能力提升**：T3L1 很适合暴露 AI 的边界。只要问题里混入“图像几何关系”这类信息，模型就容易给出看似合理但实际不对的结果。相比“让它一步到位”，更有效的方法是让我先决定结构和验收标准，再让 AI 实现底层函数、整理接口、修编译错误，我自己负责最终几何摆放与 review。
- **调试能力提升**：过程中遇到了 QEMU 图形后端、DMA 池大小、设备枚举位置、图形不显示等问题。相比普通算法题，这类问题更接近真实系统开发中的“环境 + 驱动 + 数据”联合调试，对我很有帮助。
- **代价**：这类实验的反馈回路比纯 `cargo test` 慢得多，需要结合 QEMU 图形窗口和串口日志一起判断；而且图案是否“像”参考图，最后仍需要人工目测，不太容易完全自动化验证。

### 3. 与本校现有实验教程的对比分析

| 对比维度 | 原教程（ch1） | 我的实验（T3L1 图形扩展） |
| ---- | ---- | ---- |
| **覆盖范围** | 裸机入口、SBI、串口输出 | 裸机入口、SBI、VirtIO-GPU、framebuffer、图元栅格化 |
| **可视化反馈** | 只有终端文本 | 有 QEMU 图形窗口，结果更直观 |
| **工程复杂度** | 较低，聚焦最小启动链路 | 更高，需要同时处理运行参数、驱动初始化和图形数据 |
| **调试方式** | 看串口输出即可 | 需要结合串口日志 + 图形窗口一起判断 |
| **可拓展性** | 适合作为后续内核实验的启动底座 | 适合作为后续图形/小游戏/逐块动画实验的显示底座 |
| **教学体验** | 强调“为什么裸机程序能跑” | 在保留启动流程教学价值的同时，增加了更强的成果感和可视化吸引力 |

总结来看，原教程更适合讲清“最小执行环境”的原理；而 T3L1 在不破坏 ch1 主线结构的前提下，把成果从“能输出字符串”提升到了“能驱动图形设备显示图案”。从学习体验上说，这种可视化的正反馈更强，也更能帮助我把抽象的启动流程、内存分配和设备驱动联系起来。
